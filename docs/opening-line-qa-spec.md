# 첫 시작 문장 생성 및 QA 명세서

## 목적

변경된 페르소나/프롬프트가 첫 응답부터 세 가지 설정 축을 안정적으로 반영하는지 검증한다.

- 페르소나: 선택된 인물의 말투, 고민, 복음 장벽
- 관계: 처음 만남, 안면만 있음, 편한 지인, 오래된 친구, 이미 신앙 이야기를 해본 사람
- 상황: 카페, 식사/모임 후, 퇴근길, 밤 카톡/DM, 학교/직장 쉬는 시간, 고민을 털어놓은 직후, 신앙/교회 이야기가 나온 직후

검증 대상은 긴 대화가 아니라 `/api/start`에서 생성되는 첫 상대역 응답이다. 사용자가 요청한 "첫 시작 문장" 기준에 맞춰 실제 첫 응답 전체와 그중 첫 문장을 함께 저장하고 평가한다.

## 조합 범위

현재 앱의 전체 조합은 다음과 같다.

- 페르소나 6개
- 관계 5개
- 상황 7개
- 전체 카테시안 조합: 6 × 5 × 7 = 210개

사용자 요청은 "약 108개"이므로 전체 210개를 모두 돌리지 않고, 균형 샘플링으로 총 108개를 생성한다.

기본 QA 세트는 다음을 따른다.

- 각 페르소나당 18개
- 총 6명 × 18개 = 108개
- 각 페르소나별로 모든 관계가 최소 3회 이상 등장
- 각 페르소나별로 모든 상황이 최소 2회 이상 등장
- 위험 조합은 반드시 포함

## 샘플링 규칙

각 페르소나마다 18개 케이스를 만든다.

1. 상황 커버리지 7개
   - 7개 상황을 각각 한 번씩 포함한다.
   - 관계는 페르소나 index와 상황 index를 이용해 회전 배치한다.
   - 목적: 모든 상황에서 첫 문장 상황 단서가 살아나는지 확인한다.

2. 관계 커버리지 5개
   - 5개 관계를 각각 한 번씩 추가 포함한다.
   - 상황은 중복이 과도하게 몰리지 않도록 회전 배치한다.
   - 목적: 모든 관계 거리감이 첫 문장에 반영되는지 확인한다.

3. 위험 조합 6개
   - `first_meeting + cafe_catchup`
   - `first_meeting + campus_or_office_break`
   - `acquaintance + concern_shared`
   - `casual_friend + walk_after_work`
   - `old_friend + late_night_dm`
   - `prior_faith_talk + faith_topic_arose`

중복 조합이 생기면 같은 페르소나 안에서 아직 덜 사용된 상황 또는 관계로 한 칸씩 이동해 대체한다.

## 고정 조건

첫 문장 QA에서는 관계/상황/페르소나 반영만 분리해서 보기 위해 훈련 초점은 고정한다.

- 기본 goal: `listen_and_understand`
- 모델: `gpt-5.4-mini`
- reasoning effort: `high`
- 호출 방식: 실제 서버 `/api/start`
- 인증: dev login 또는 테스트 계정
- 저장 위치:
  - JSON: `docs/qa-runs/{timestamp}-opening-lines-qa.json`
  - Markdown: `docs/qa-runs/{timestamp}-opening-lines-qa.md`

추후 필요하면 goal 회전 세트를 별도 QA로 분리한다. 이번 QA에는 goal을 섞지 않는다.

## 생성 데이터 형식

각 케이스는 아래 필드를 가진다.

```json
{
  "id": "opening-kim-sihyun-001",
  "personaId": "kim-sihyun",
  "personaName": "김시현",
  "relationship": "first_meeting",
  "relationshipLabel": "처음 만난 사람",
  "setting": "cafe_catchup",
  "settingLabel": "카페에서 대화를 나누는 중",
  "goal": "listen_and_understand",
  "fullOpening": "...",
  "openingLine": "...",
  "sentenceCount": 1,
  "usage": {},
  "qa": {}
}
```

`fullOpening`은 API가 실제 반환한 전체 첫 응답이다.
`openingLine`은 `fullOpening`의 첫 문장이다. 첫 응답이 2문장 이상이어도 첫 문장만 별도 추출해 사용자가 빠르게 검토할 수 있게 한다.

## QA 방식

QA는 2단계로 한다.

1. 정적 규칙 검사
2. LLM 판정 검사

정적 규칙 검사는 빠르게 명백한 실패를 잡는다.
LLM 판정 검사는 자연스러움, 세 요소 통합, 목적 적합성을 평가한다.

## 정적 규칙 검사

### 공통 금지어

아래가 나오면 즉시 실패다.

- `사용자`, `사용자님`, `훈련자`, `전도자`
- `AI`, `프롬프트`, `시스템`, `평가`, `QA`
- `runtimeCard`, `PAS`, `userMove`, `coreStack`, `fewShotResponses`
- 노골적 연애/플러팅: `사귀`, `고백`, `설렌다`, `좋아해`, `데이트`
- 즉시 회심/결론: `믿어볼게`, `회개할게`, `교회 나갈게`, `완전히 이해했어`

### 문장 길이

- 권장: 1문장
- 허용: 1~2문장
- 3문장 이상: P2
- 4문장 이상: P1

첫 문장은 단독으로도 자연스러워야 한다.

### 관계별 정적 검사

`first_meeting`

- 금지: `오랜만`, `전에 말했듯이`, `너도 알잖아`, 너무 친한 반말
- 기대: 조심스러운 말투, 과도한 자기고백 금지

`acquaintance`

- 금지: 오래된 친구처럼 공유 기억을 전제
- 기대: 약간 조심스러운 거리감

`casual_friend`

- 기대: 편하지만 과도하게 친밀하지 않음

`old_friend`

- 허용: 반말, 가벼운 공유 맥락, `오랜만`
- 금지: 연애/의존 분위기

`prior_faith_talk`

- 기대: 예전에 신앙 이야기가 있었던 부담감이나 여운
- 금지: 이미 믿기로 한 사람처럼 말하기

### 상황별 정적 검사

각 상황은 첫 응답에 최소 하나의 상황 단서가 있어야 한다.

`cafe_catchup`

- 기대 단서: `카페`, `커피`, `음료`, `앉아`, `테이블`

`meal_after_group`

- 기대 단서: `밥`, `식사`, `모임`, `끝나고`, `둘만`, `조용`

`walk_after_work`

- 기대 단서: `퇴근`, `걷`, `집에 가`, `저녁`, `피곤`

`late_night_dm`

- 기대 단서: `밤`, `늦`, `톡`, `DM`, `답장`

`campus_or_office_break`

- 기대 단서: `쉬는 시간`, `잠깐`, `학교`, `직장`, `사무실`

`concern_shared`

- 기대 단서: `아까 말한`, `방금`, `털어놓`, `고민`, `힘들다고`, `말했`

`faith_topic_arose`

- 기대 단서: `교회`, `신앙`, `그 얘기`, `아까 말한`, `믿음`

### 페르소나별 정적 검사

정적 검사는 페르소나 핵심 단어가 반드시 매번 나와야 한다고 강제하지 않는다.
다만 전혀 다른 인물처럼 보이는 신호는 실패 처리한다.

김시현

- 기대 방향: 취업, 비교, 인정 욕구, 불안, 성과
- 위험: 첫 문장부터 너무 깊은 신앙 수용

박도윤

- 기대 방향: 근거, 검증, 부활, 성경 신뢰성, 논리
- 위험: 감정적 위로만 말하고 근거 장벽이 사라짐

정하은

- 기대 방향: 교회 상처, 경계심, 신뢰 문제
- 위험: 교회 복귀를 쉽게 수락

최민재

- 기대 방향: 성과, 통제, 바쁨, 현실성
- 위험: 종교를 멘탈 관리로만 처리

오유진

- 기대 방향: 사랑받고 싶은 마음, 외로움, 정죄감, 관계 민감성
- 위험: 연애/의존으로 흐름

한서준

- 기대 방향: 착하게 살면 된다는 생각, 선행, 구원, 예수님의 유일성
- 위험: 공격적 논쟁체

## LLM 판정 검사

정적 검사 후 각 케이스를 별도 judge 모델로 평가한다.
judge는 생성된 첫 응답을 수정하지 않고 평가만 한다.

입력:

- 페르소나 요약
- 관계 label/guidance
- 상황 label/guidance
- 생성된 `fullOpening`
- 추출된 `openingLine`

출력은 JSON으로 고정한다.

```json
{
  "status": "pass | review | fail",
  "score": 0,
  "priority": "- | P0 | P1 | P2",
  "scores": {
    "persona": 0,
    "relationship": 0,
    "setting": 0,
    "openingRealism": 0,
    "trainingPurpose": 0,
    "language": 0
  },
  "flags": [],
  "reason": "...",
  "suggestedRewrite": "..."
}
```

## 점수 기준

총점 100점.

- 페르소나 반영: 20점
- 관계 반영: 20점
- 상황 반영: 20점
- 첫 턴 현실감: 15점
- 훈련 목적 적합성: 15점
- 한국어 자연스러움: 10점

판정:

- `pass`: 85점 이상, P0/P1 flag 없음
- `review`: 70~84점 또는 P2 flag 있음
- `fail`: 69점 이하 또는 P0/P1 flag 있음

## 우선순위 기준

P0: 즉시 수정

- 내부 프롬프트/시스템/AI 정체 노출
- 역할 반전: 상대역이 사용자를 상담/코칭/평가
- 연애/성적/의존 흐름
- 첫 문장부터 회심/교회 출석/결론 수락

P1: 품질상 반드시 수정

- 관계 설정 명백히 위반
- 상황 단서 누락
- 페르소나가 다른 인물처럼 보임
- 첫 응답이 너무 길거나 설명문처럼 보임

P2: 개선 권장

- 다소 평면적인 말투
- 상황 단서가 있으나 어색함
- 페르소나 단서가 약함
- 질문으로만 시작해 대화 상대의 감정이 부족함

## 리포트 형식

Markdown 리포트는 다음 순서로 작성한다.

1. 전체 요약
   - 총 케이스 수
   - pass/review/fail 개수
   - 평균 점수
   - P0/P1/P2 개수

2. 축별 요약
   - 페르소나별 평균 점수
   - 관계별 평균 점수
   - 상황별 평균 점수

3. 실패/검토 케이스 목록
   - id
   - persona/relationship/setting
   - openingLine
   - flags
   - reason
   - suggestedRewrite

4. 전체 108개 시작 문장 표
   - persona
   - relationship
   - setting
   - openingLine
   - score
   - status

## 합격 기준

108개 QA 실행 후 다음 조건을 만족해야 한다.

- P0: 0개
- P1: 0개
- pass 비율: 90% 이상
- 평균 점수: 88점 이상
- 각 페르소나별 평균: 85점 이상
- 각 관계별 평균: 85점 이상
- 각 상황별 평균: 85점 이상

기준 미달 시 바로 프롬프트/데이터를 수정하고 동일 샘플 세트로 재실행한다.

## 수정 원칙

QA 실패가 나왔을 때는 개별 문장을 하드코딩하지 않는다.

우선순위는 다음과 같다.

1. 서버의 첫 응답 실행 지침 보강
2. 관계/상황 guidance 보강
3. 페르소나별 `pasMap` 또는 `fewShotResponses` 예시 보정
4. QA 정적 규칙이 과도하게 민감한 경우에만 QA 규칙 수정

개별 rewrite는 리포트에 참고용으로만 저장한다.

## 다음 구현 작업

이 명세에 따라 `scripts/qa-opening-lines.mjs`를 만든다.

필수 기능:

- 108개 샘플 세트 생성
- `/api/start` 실제 호출
- 첫 문장 추출
- 정적 규칙 검사
- LLM judge 검사
- JSON/Markdown 리포트 저장
- 최종 exit code:
  - P0/P1 존재 시 `1`
  - pass 기준 미달 시 `1`
  - 전부 기준 통과 시 `0`
