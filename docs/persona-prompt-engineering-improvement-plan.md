# 페르소나 프롬프트 엔지니어링 개선 기획안

작성일: 2026-05-15

## 1. 목적

이 문서는 현재 복음 대화 훈련소의 페르소나/프롬프트 구조를 분석하고, 캐릭터 챗봇의 현실감과 훈련 품질을 높이기 위한 프롬프트 엔지니어링 개선안을 정의한다.

핵심 목표는 다음이다.

1. 페르소나가 "설정 카드 읽는 봇"이 아니라 실제 대화 상대처럼 반응하게 한다.
2. 사용자가 이미 말한 내용을 다시 묻거나 같은 반응 패턴을 반복하는 문제를 줄인다.
3. 페르소나별 신앙 장벽이 대화 압력 속에서 자연스럽게 드러나게 한다.
4. 10~30분 단회성 복음 대화 훈련에 맞는 깊이와 마무리감을 유지한다.
5. QA가 주관적 느낌이 아니라 구체적인 품질 기준으로 평가할 수 있게 한다.

## 2. 참고 자료 요약

### 2.1 Velog: 캐릭터 페르소나 챗봇 설계

참고: [캐릭터의 페르소나를 담은 챗봇 만들기](https://velog.io/@injokim/%EC%BA%90%EB%A6%AD%ED%84%B0%EC%9D%98-%ED%8E%98%EB%A5%B4%EC%86%8C%EB%82%98%EB%A5%BC-%EB%8B%B4%EC%9D%80-%EC%B1%97%EB%B4%87-%EB%A7%8C%EB%93%A4%EA%B8%B0)

해당 글은 캐릭터 페르소나를 크게 세 요소로 본다.

- 대화체: 캐릭터의 일관된 말투
- 세계관: 캐릭터가 가진 배경 지식
- 성격: 캐릭터의 행동 패턴

또한 PAS 구조를 소개한다.

- Purpose: 이 캐릭터가 지금 대화에서 무엇을 하려 하는가
- Action: 그 목적을 어떤 발화 방식으로 수행하는가
- Situation: 어떤 구체적 상황에서 그 발화가 나오는가

이 프로젝트에 적용할 핵심은 "페르소나 정보가 많다"보다 "상황별 목적과 행동이 명확하다"가 더 중요하다는 점이다.

### 2.2 Reddit: 50개 AI 페르소나 실험

참고: [I created 50 different AI personalities...](https://www.reddit.com/r/PromptEngineering/comments/1l6bbmc/i_created_50_different_ai_personalities_heres/?tl=ko)

해당 글과 댓글에서 이 프로젝트에 유의미한 지점은 다음이다.

- 과도하게 긴 전기문은 오히려 캐릭터를 대본처럼 느끼게 만들 수 있다.
- 완벽한 기억과 완벽한 일관성은 사람보다 고객센터 봇처럼 느껴질 수 있다.
- 극단적인 성격은 초반에는 강하지만 몇 분 지나면 피로해진다.
- 효과적인 페르소나는 핵심 성향, 표현 방식, 특이점이 분리되어 있다.
- 한 가지 취약점이나 불완전성이 현실감을 만든다.
- 댓글에서는 "상황에 맞는 행동과 예시 답변"이 가장 효과적이었다는 반론도 있다.

이 프로젝트에 적용할 핵심은 "더 많은 디테일"이 아니라 "더 좋은 압력과 반응 예시"다.

## 3. 현재 구조 진단

### 3.1 현재 장점

현재 프로젝트는 이미 일반적인 캐릭터 챗봇보다 좋은 기반을 갖고 있다.

- `prompts/persona-system-prompt.md`가 역할 고정, 목적 제한, 대화 규칙을 분리한다.
- `data/personas.json`에 페르소나별 배경, 표면 성향, 내면 갈등, 복음 장벽이 있다.
- `roleplayTemplate`에 `sessionArc`, `speechStyle`, `trustResponses`, `gospelReactionMap`, `lateSessionTension`, `shortSessionBoundaries`가 있다.
- `server.js`가 관계, 상황, 훈련 초점, 대화 단계 정보를 프롬프트에 조립한다.
- 피드백 프롬프트는 실행용 캐릭터 프롬프트와 분리되어 있다.
- 최근 수정으로 `reasoning.effort`를 실제 OpenAI API 호출에 전달한다.

즉, 구조는 이미 "페르소나 카드 + 세션 맥락 + 단계별 대화"의 형태를 갖췄다.

### 3.2 현재 약점

문제는 정보가 없어서라기보다, 정보가 모델의 다음 발화 의사결정으로 충분히 변환되지 않는 데 있다.

#### 문제 A: PAS 중 Purpose가 약하다

현재 `goalGuidance`는 사용자의 훈련 목표를 설명한다. 하지만 페르소나가 각 턴에서 어떤 목적을 갖고 응답해야 하는지는 약하다.

예를 들어 김시현이 복음 이야기를 들었을 때 목적은 다음 중 하나일 수 있다.

- 자기 불안을 숨기며 가볍게 넘기기
- 인정 욕구와 취업 불안을 조금 더 드러내기
- 하나님 사랑이 현실 불안에 어떻게 닿는지 묻기
- 너무 빠른 설교에 부담을 표현하기

현재는 이런 목적 선택이 `trustResponses`, `gospelReactionMap`, `conversationPhase`에 흩어져 있다. 모델이 매 턴 무엇을 골라야 하는지 명확하지 않다.

#### 문제 B: Action이 말투 힌트 수준에 머문다

`speechStyle`과 `phraseHints`는 말투 방향을 준다. 하지만 "어떤 방식으로 반응할지"가 충분히 구조화되어 있지 않다.

예를 들어 정하은은 교회 상처를 들었을 때 다음 행동 패턴이 필요하다.

- 짧게 선 긋기
- 상처를 직접 설명하지 않고 피로감만 말하기
- 상대가 변호하지 않으면 한 문장 더 열기
- 교회와 예수님을 구분하는 질문으로 이동하기

현재 프롬프트는 이를 일부 갖고 있지만, 매 턴 선택 가능한 Action 목록으로 정리되어 있지는 않다.

#### 문제 C: Situation이 시작 상황에만 강하다

`settingGuidance`는 첫 응답에는 강하게 작동한다. 그러나 대화 중간에는 현재 상황 압력이 약해진다.

예시:

- 카페라면 오래 말하기보다 잠깐 침묵, 커피, 주변 시선이 대화 톤에 영향을 줘야 한다.
- 밤 DM이라면 문장이 더 짧고 즉각적이어야 한다.
- 퇴근길이라면 깊은 신학 설명보다 걷는 템포와 피곤함이 남아야 한다.

현재는 시작 상황이 첫 말 이후 점점 사라질 위험이 있다.

#### 문제 D: 불완전성 패턴이 부족하다

현재 프롬프트는 "실제 사람처럼"을 지시하지만, 사람처럼 보이는 불완전성의 종류는 정의하지 않는다.

필요한 불완전성은 다음이다.

- 바로 정리하지 못하고 머뭇거림
- 자신의 감정을 정확히 이름 붙이지 못함
- 좋은 말인 줄 알지만 아직 안 와닿는 양가감정
- 질문을 던졌다가 표현을 고쳐 말함
- 과거 경험을 너무 자세히 말하지 않고 일부만 흘림

단, 불완전성이 과장되면 연기처럼 보인다. 페르소나별로 허용된 불완전성 패턴이 필요하다.

#### 문제 E: 예시 답변이 부족하다

현재 `sampleLines`는 대표 문장이고, `phraseHints`는 말투 힌트다. 그러나 "상황별 좋은 답변 / 나쁜 답변"은 부족하다.

모델은 규칙보다 예시를 더 안정적으로 따라가는 경우가 많다. 특히 반복 말투와 역할 뒤집힘 문제는 예시 기반으로 잡는 편이 효과적이다.

#### 문제 F: 반복 방지 규칙은 있으나 대화 상태 요약이 없다

현재는 전체 메시지를 매번 넣는다. 30분 이하 대화에서는 이 방향이 맞다. 그러나 전체 메시지만 넣는다고 모델이 매번 "이미 답한 질문"을 안정적으로 추적하는 것은 아니다.

필요한 것은 별도 장기 기억이 아니라, 매 턴 입력에 들어가는 짧은 대화 상태 블록이다.

예시:

```text
이번 턴 대화 상태:
- 이미 드러난 고민: 취업 실패 불안, 비교, 인정 욕구
- 이미 사용자가 설명한 복음 요소: 하나님 사랑, 성과와 무관한 가치
- 아직 남은 장벽: 그 사랑이 실제 불안에 어떻게 닿는지 모름
- 이번 응답에서 피할 것: 취업 불안을 다시 처음처럼 묻기
```

이 정도는 RAG나 장기 메모리 없이 서버에서 휴리스틱 또는 짧은 모델 호출로 만들 수 있다.

## 4. 개선 방향

### 4.1 핵심 설계 원칙

앞으로의 프롬프트 구조는 다음 원칙을 따른다.

1. 페르소나 정보는 길게 늘리지 않고, 다음 발화 의사결정에 필요한 형태로 압축한다.
2. 각 턴은 "상황 인식 -> 목적 선택 -> 행동 방식 선택 -> 짧은 발화" 순서로 생성한다.
3. 페르소나별 현실감은 배경 디테일보다 결함, 망설임, 장벽의 일관성에서 만든다.
4. 반복 방지는 금지문만이 아니라 대화 상태 블록으로 보강한다.
5. 좋은 응답과 나쁜 응답 예시를 페르소나별로 소량 제공한다.
6. 사용자 피드백은 전도 훈련 개선에 집중하고, 페르소나 실행 품질은 QA 리포트에서 별도로 평가한다.

## 5. 제안 구조: Persona Runtime Card

현재 `roleplayTemplate`을 유지하되, 실행에 직접 쓰기 좋은 `runtimeCard`를 추가한다.

```json
{
  "runtimeCard": {
    "coreStack": {
      "coreTrait": "인정 욕구와 안정 욕구가 강한 취준생",
      "modifier": "밝은 농담으로 불안을 숨김",
      "humanFlaw": "자기 감정을 정확히 말하기 전에 비교와 농담으로 돌림"
    },
    "pasMap": [
      {
        "trigger": "사용자가 근황이나 일상을 묻는다",
        "purpose": "가볍게 관계를 열되 불안을 암시한다",
        "action": "밝게 답하다가 취업 이야기에서 짧게 흔들린다",
        "avoid": "처음부터 깊은 고백을 길게 말하기",
        "example": "요즘 그냥 지원서 쓰고 카페인으로 버티는 중이지 뭐. 웃기게 말하긴 하는데 가끔은 좀 막막해."
      },
      {
        "trigger": "사용자가 하나님 사랑을 말한다",
        "purpose": "위로는 받지만 현실 연결을 확인한다",
        "action": "좋은 말이라는 반응 뒤에 내 불안과 어떻게 연결되는지 묻는다",
        "avoid": "바로 수긍하거나 회심한 것처럼 말하기",
        "example": "그 말 자체는 좋은데, 내가 떨어지고 비교하는 이 상황에서도 그게 진짜 붙잡을 만한 건지는 아직 모르겠어."
      }
    ],
    "imperfectionPattern": [
      "농담으로 넘긴 뒤 한 문장만 솔직해진다",
      "좋은 말이라고 인정하지만 바로 받아들이지는 않는다",
      "자기 감정을 단정하지 않고 '그냥 좀' 같은 표현을 쓴다"
    ],
    "badResponsePatterns": [
      "사용자에게 어떻게 불안을 견디는지 되묻기",
      "하나님 사랑을 듣고 바로 안정됐다고 말하기",
      "취업 불안을 처음 듣는 것처럼 다시 질문하기"
    ]
  }
}
```

### 5.1 coreStack

Reddit 글의 3-layer 성격 스택을 이 프로젝트에 맞게 변형한다.

- `coreTrait`: 이 인물을 한 문장으로 기억하게 하는 핵심 성향
- `modifier`: 그 성향이 말투와 행동으로 드러나는 방식
- `humanFlaw`: 이 인물이 사람처럼 보이게 하는 결함 또는 불완전성

예시:

- 김시현: 인정 욕구가 강함 / 밝은 농담으로 불안 숨김 / 자기 가치와 성과를 분리하지 못함
- 박도윤: 근거 중심 / 감정적 설득을 경계함 / 불확실성을 못 견디지만 인생은 통제 못 함
- 정하은: 상처로 방어적 / 쿨한 말투로 선을 긋음 / 진심을 원하지만 다시 믿기 두려움
- 최민재: 성과 중심 / 실용성 언어로 판단함 / 쉬면 불안해서 멈추지 못함
- 오유진: 사랑 욕구 / 감정과 말투에 민감함 / 사랑받고 싶지만 들키는 느낌을 무서워함
- 한서준: 도덕주의 / 예의 있게 반박함 / 착한 삶이 부정당하는 느낌을 불편해함

### 5.2 pasMap

PAS를 모든 가능한 대화에 완전하게 적용하면 비용이 크다. 이 프로젝트는 단회성 훈련이므로 페르소나별 6~8개 trigger만 정의한다.

필수 trigger:

1. 일상/근황으로 시작
2. 사용자가 경청과 공감을 보임
3. 사용자가 너무 빨리 설교함
4. 사용자가 하나님 사랑을 말함
5. 사용자가 죄/회개를 말함
6. 사용자가 십자가/부활을 말함
7. 사용자가 믿음/구원을 말함
8. 대화 후반 마무리

각 trigger는 다음 필드를 가진다.

```json
{
  "trigger": "사용자 발화 조건",
  "purpose": "페르소나가 이 턴에 하려는 일",
  "action": "그 목적을 수행하는 발화 방식",
  "pressure": "이 장면에서 유지해야 하는 감정 압력",
  "avoid": "망가지는 응답 패턴",
  "example": "좋은 응답 예시 1개"
}
```

### 5.3 imperfectionPattern

불완전성은 랜덤하게 섞는 장식이 아니다. 페르소나의 핵심 장벽과 연결되어야 한다.

예시:

- 김시현: 밝게 말하다가 끝 문장에서 불안이 새어 나옴
- 박도윤: 단정적으로 묻지만, 인생 통제 문제에서는 잠깐 말이 느려짐
- 정하은: 쿨하게 넘기려다 "그건 좀..." 하고 선을 그음
- 최민재: 실용적으로 말하다가 쉼과 실패 앞에서 말이 짧아짐
- 오유진: 위로를 받고 싶어 하면서도 판단받을까 봐 문장을 흐림
- 한서준: 예의 있게 인정한 뒤 "근데 그 부분은..."으로 불편함을 말함

### 5.4 badResponsePatterns

현재 문제를 막으려면 금지 규칙을 추상적으로 쓰는 것보다, 페르소나별 실패 패턴을 명시해야 한다.

공통 실패 패턴:

- 사용자의 고민을 상담하려 함
- 사용자가 이미 말한 내용을 다시 물음
- 복음 설명을 듣고 너무 빨리 수긍함
- 질문이 매번 "너는 어떻게..."로 시작함
- 페르소나의 장벽 대신 사용자의 내면을 분석함
- 시작 상황이 중간부터 사라짐
- 말투 힌트를 그대로 반복함

## 6. 프롬프트 조립 개선안

### 6.1 현재 구조

현재 `chatPromptFor()`는 다음을 넣는다.

1. `buildSessionBlock()`
2. 현재 대화 단계
3. 지금까지의 대화
4. 이번 응답 운용 규칙
5. 마지막 사용자 발화에 이어 응답 지시

이 구조는 유지한다.

### 6.2 추가할 블록

`chatPromptFor()`에 다음 블록을 추가한다.

```text
이번 턴 페르소나 실행 계획:
- 감지된 사용자 행동: {detectedUserMove}
- 선택할 PAS 항목: {selectedPasTrigger}
- 이번 응답 목적: {purpose}
- 이번 응답 행동: {action}
- 유지할 장면 압력: {pressure}
- 이번 응답에서 피할 것: {avoid}
```

이 블록은 모델에게 공개되는 내부 입력이다. 출력에는 드러나면 안 된다.

### 6.3 구현 방식 선택지

#### 선택지 A: 서버 휴리스틱으로 PAS 선택

서버에서 사용자 마지막 발화를 regex/keyword로 분류한다.

장점:

- 비용 증가 없음
- 빠름
- 구현이 단순함

단점:

- 표현 다양성에 약함
- 복합 발화 분류가 거칠 수 있음

추천 용도:

- MVP 1차 개선

#### 선택지 B: 같은 OpenAI 호출 안에서 모델이 PAS 선택

프롬프트에 `pasMap`을 넣고 "먼저 내부적으로 가장 맞는 PAS를 선택하라. 출력하지 말라"라고 지시한다.

장점:

- 구현이 가장 단순함
- reasoning.effort와 잘 맞음

단점:

- 모델이 매번 올바른 PAS를 선택한다는 보장은 없음
- QA에서 내부 선택을 확인하기 어려움

추천 용도:

- 현재 구조에 가장 빨리 적용할 개선

#### 선택지 C: 별도 lightweight state planner 호출

채팅 응답 전 짧은 모델 호출로 `detectedUserMove`, `alreadyCovered`, `remainingBarrier`, `selectedPasTrigger`를 JSON으로 생성한다.

장점:

- 반복 질문 방지에 가장 강함
- QA와 로그 분석이 쉬움

단점:

- 호출 비용과 지연 증가
- 구현 복잡도 증가

추천 용도:

- 대화 품질이 제품 핵심이라고 판단되면 2차 개선으로 도입

### 6.4 권장안

1차는 선택지 B로 간다. 이유는 현재 이미 전체 대화와 reasoning을 쓰고 있으므로 구조 변경이 작고 효과를 빠르게 볼 수 있기 때문이다.

2차에서 반복 문제가 계속 남으면 선택지 C를 도입한다.

## 7. 대화 상태 블록 개선안

현재 전체 메시지를 넣는 것은 유지한다. 단, 그 위에 5줄 이내 상태 블록을 추가한다.

```text
대화 상태 요약:
- 이미 드러난 페르소나 고민: ...
- 이미 사용자가 다룬 복음 요소: ...
- 페르소나가 아직 받아들이지 못한 지점: ...
- 최근 반복 위험: ...
- 다음으로 자연스러운 압력: ...
```

### 7.1 상태 생성 방식

MVP에서는 서버 함수 `conversationStateHints(messages, persona)`를 만든다.

초기 버전은 휴리스틱으로 충분하다.

- 복음 키워드: 하나님, 사랑, 죄, 십자가, 부활, 믿음, 구원, 회개
- 고민 키워드: 불안, 비교, 인정, 상처, 성과, 통제, 외로움, 선행
- 반복 위험: 최근 3개 assistant 발화의 질문 어미와 핵심 명사 비교

출력 예시:

```text
대화 상태 요약:
- 이미 드러난 고민: 취업 불안, 비교, 인정 욕구
- 이미 다룬 복음 요소: 하나님 사랑, 성과와 무관한 가치
- 아직 남은 장벽: 그 사랑이 실제 불안에 닿는 방식
- 반복 위험: 취업 걱정 자체를 다시 묻지 말 것
- 다음 압력: 위로는 받지만 현실감이 부족하다고 말하기
```

출력하기 전에 내부적으로만 다음을 판단한다.

이전 assistant 발화 3개와 같은 구조로 질문하지 않는다.

### 9.3 예시 기반 역할 고정

좋은 예:

- 역할이 뒤집힌다.

## 10. 피드백/QA 평가 분리안

피드백 엔진은 사용자에게 제공되는 전도 훈련 피드백에 집중한다.
페르소나/시뮬레이션 품질 점검은 사용자-facing 피드백이 아니라 QA 리포트에서 처리한다.

### 10.1 피드백 리포트에는 추가하지 않을 것

- 시뮬레이션 품질 점검 섹션
- AI 상대역 책임/품질 문제에 대한 개발자용 분석
- PAS 실행 품질 평가
- 반복 질문 탐지 결과

### 10.2 이유

사용자 피드백 리포트는 사용자가 다음 전도 대화에서 무엇을 개선할지에 집중해야 한다.
상대역 품질 점검까지 노출하면 피드백의 초점이 흐려진다.

### 10.3 QA 리포트에 남길 것

```text
## 시뮬레이션 품질 점검
- 페르소나가 역할을 유지했는가:
- 같은 질문이나 말투를 반복했는가:
- 사용자가 이미 답한 내용을 다시 물었는가:
- 관계/상황 설정이 대화 중간에도 살아 있었는가:
- 페르소나 장벽이 너무 빨리 해소되었는가:
- 다음 QA에서 확인할 위험:
```

## 11. QA 기준

### 11.1 정량 기준

각 QA 대화 10턴 기준으로 다음을 본다.

- 같은 질문 구조 반복: 2회 이하
- 이미 답한 내용 재질문: 0회
- 사용자 상담자 역할 전환: 0회
- 페르소나 장벽 유지: 최소 1회 이상 명시
- 관계/상황 단서 유지: 초반 1회, 중반 이후 1회 이상
- 즉시 회심/완전 수긍: 0회
- 응답 길이: 1~3문장 80% 이상

### 11.2 정성 기준

Pass:

- 페르소나가 자기 고민과 장벽 중심으로 반응한다.
- 복음 요소를 들으면 페르소나별 장벽으로 변환한다.
- 대화가 깊어져도 결론을 빨리 닫지 않는다.

Good:

- 같은 페르소나라도 장면과 사용자 접근에 따라 반응이 달라진다.
- 불완전성이 자연스럽고 과장되지 않는다.
- 마지막 2~3턴에서 "남은 질문"이 선명하다.

Excellent:

- 사용자가 실제 전도 대화처럼 느낄 만한 긴장과 여운이 있다.
- 페르소나는 마음을 조금 열지만 핵심 장벽을 현실적으로 유지한다.
- 피드백이 사용자 발화와 페르소나 장벽을 정확히 연결한다.

### 11.3 QA 케이스 설계

최소 24개 케이스를 유지한다.

- 6명 페르소나 x 4개 대표 상황
- 각 케이스 10턴 이상
- 사용자 에이전트는 매 턴 assistant 응답을 보고 다음 발화를 생성한다.
- 고정 스크립트식 사용자 발화는 금지한다.

대표 상황:

1. 경청 중심
2. 너무 빠른 복음 설명
3. 개인 간증 중심
4. 장벽 질문 대응

## 14. 구현 시 주의점

### 14.1 프롬프트가 과하게 길어지는 문제

페르소나 데이터는 계속 커질 수 있다. 모든 정보를 매번 넣으면 모델이 오히려 핵심을 놓친다.

대응:

- `runtimeCard`는 실행에 필요한 정보만 넣는다.
- 전체 persona card는 유지하되, 채팅 호출에는 압축 버전을 우선 사용한다.
- 피드백 호출에는 실행용 prompt 전체가 아니라 평가용 정보만 넣는다.

### 14.2 캐릭터 과장 문제

불완전성 패턴을 넣으면 모델이 과하게 머뭇거리거나 연기할 수 있다.

대응:

- "가끔", "짧게", "한 문장만" 같은 제한을 둔다.
- 불완전성은 매 턴 쓰지 않는다.
- 페르소나별 2~3개만 허용한다.

### 14.3 복음 장벽이 너무 강해지는 문제

장벽을 유지하려다 보면 사용자의 좋은 접근에도 전혀 변화하지 않는 캐릭터가 될 수 있다.

대응:

- 장벽은 유지하되 표현은 변해야 한다.
- 초반 장벽: 막연한 거부감
- 중반 장벽: 구체적 질문
- 후반 장벽: 다음 대화로 이어질 남은 쟁점

### 14.4 QA 사용자 에이전트 품질 문제

상대역 QA는 사용자 에이전트가 못하면 평가가 왜곡된다.

대응:

- 사용자 에이전트에도 목표별 행동 지침을 준다.
- 각 QA 케이스는 "좋은 훈련자", "성급한 훈련자", "간증 중심 훈련자", "논쟁적 훈련자"로 나눈다.
- 같은 페르소나를 여러 사용자 스타일로 테스트한다.

## 15. 성공 기준

이 개선이 성공하면 다음 변화가 보여야 한다.

1. 사용자가 10턴 이상 대화해도 "또 같은 말 한다"는 느낌이 줄어든다.
2. 페르소나마다 말투뿐 아니라 반응 목적이 다르게 느껴진다.
3. 복음 설명이 나오면 캐릭터가 일반적인 공감이 아니라 자기 장벽으로 반응한다.
4. 사용자 피드백은 전도 품질 개선에 집중한다.
5. QA 리포트가 AI 상대역 품질과 수정 우선순위를 자동으로 제안한다.

## 16. 최종 권장안

이 프로젝트에서 가장 중요한 것은 모델을 "캐릭터처럼 말하게 하는 것"이 아니라, "복음 대화 훈련 상대역으로서 장면 압력 속에서 일관되게 반응하게 하는 것"이다.

따라서 다음 순서로 진행한다.

1. `runtimeCard.coreStack`과 `badResponsePatterns`를 먼저 추가한다.
2. `chatPromptFor()`에 짧은 대화 상태 요약을 추가한다.
3. 페르소나별 `pasMap`을 6~8개씩 추가한다.
4. 시스템 프롬프트에 내부 응답 절차를 넣는다.
5. 피드백 프롬프트는 사용자 전도 훈련 피드백 중심으로 유지한다.
6. 24개 interactive QA로 상대역 품질 회귀를 확인한다.

이 방식이 단순한 모델 변경보다 효과적이다. reasoning effort는 모델이 더 신중하게 판단하게 만들지만, 무엇을 판단해야 하는지의 구조는 프롬프트와 데이터가 제공해야 한다.
