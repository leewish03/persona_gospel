# 페르소나/프롬프트 대화 품질 개선 기획 및 구현 명세

작성일: 2026-05-19

## 1. 목적

이 문서는 복음 대화 훈련소의 페르소나/프롬프트 품질을 `대화 품질 중심`으로 개선하기 위한 실행 명세다.

이번 개선의 목표는 첫 문장만 더 예쁘게 만드는 것이 아니다. 사용자가 10~30분 동안 훈련할 때 상대역이 실제 사람처럼 일관되게 반응하고, 반복 질문이나 역할 뒤집힘 없이 페르소나의 고민과 복음 장벽을 자연스럽게 유지하도록 만드는 것이다.

개선 축은 세 가지다.

1. 첫 장면/오프닝: `visibleScene`과 `openingLine`의 역할을 분리한다.
2. 대화 중 페르소나 응답: 반복, 역할 뒤집힘, 과도한 수긍, 장벽 소실을 줄인다.
3. 페르소나 데이터: 각 인물의 핵심 장벽, 말투, 불완전성, PAS, few-shot을 더 실행 가능한 데이터로 재정리한다.

## 2. 현재 구조와 문제 진단

### 2.1 현재 구조

현재 서버는 다음 구조로 프롬프트를 만든다.

- `buildSessionBlock(session, persona)`: 역할 고정, 단회성 훈련 원칙, 관계/상황/목표 지침, 페르소나 요약을 조립한다.
- `formatRuntimeCard(persona)`: `coreStack`, `sessionArc`, `speechStyle`, `gospelReactionMap`, `pasMap`, good/bad few-shot을 압축한다.
- `initialPromptFor(session, persona)`: 첫 응답을 생성한다.
- `chatPromptFor(session, persona, messages)`: 대화 단계, 대화 상태 힌트, 반복 위험, PAS 실행 계획, 전체 메시지를 넣어 다음 응답을 생성한다.
- `visibleSceneFor(session, persona)`: 채팅 상단에 표시할 3인칭 현재 장면 설명을 만든다.
- 관리자 첫문장 생성은 `visibleScene + openingLine` 형식을 사용한다.

### 2.2 108개 첫문장 결과에서 확인된 문제

이전 생성 결과에서 확인된 대표 실패 유형은 다음이다.

- 앞맥락 지시: `이런 얘기`, `그 얘기`, `저번`, `아까`, `방금`처럼 사용자가 보지 못한 이전 사건을 참조한다.
- 메타 대화 시작: `뭐부터 시작하면 좋을지`, `이런 얘기 꺼내는 게`처럼 대화 시작 자체를 화제로 삼는다.
- 상대 발화 전제: `커피 맛있다고 하셨는데`, `말 걸어주셔서`, `답장 왔네요`처럼 사용자가 아직 하지 않은 말을 전제한다.
- 일반 스몰토크: `커피 뭐 시키셨어요?`, `조용해졌네요`처럼 페르소나 고유성이 약하다.
- 길이 초과: 첫 대사가 설명문처럼 길어져 말풍선 시작점으로 부적합하다.

핵심 원인은 금지어 부족이 아니라 시간축 혼선이다. 일부 상황 라벨은 `고민을 털어놓은 직후`, `신앙 이야기가 언급된 직후`, `이미 신앙 이야기를 해본 사람`처럼 앞사건을 암시한다. 모델은 이를 이미 진행 중인 대화의 한 턴으로 해석한다.

### 2.3 대화 중 품질 리스크

첫문장 이후 대화에서는 다음 위험이 남아 있다.

- 질문 반복: `어떻게`, `왜`, `뭐가 다른데`류 질문 구조가 반복된다.
- 역할 뒤집힘: 페르소나가 사용자의 내면이나 대처법을 상담하듯 묻는다.
- 장벽 소실: 복음 설명을 들은 뒤 페르소나가 너무 빨리 수긍하거나 회심한 듯 반응한다.
- 페르소나 희석: 페르소나별 장벽이 아니라 일반적인 `좋은 말인데 아직 모르겠다` 패턴으로 수렴한다.
- 상황 단절: 첫 장면은 보였지만 대화 중반 이후 카페/퇴근길/밤 톡 같은 장면 압력이 사라진다.

## 3. 첫 장면/오프닝 개선 명세

### 3.1 역할 정의

첫 장면은 두 요소로 분리한다.

- `visibleScene`: 채팅 상단에 표시되는 3인칭 현재 상황 설명이다.
- `openingLine`: 페르소나의 첫 말풍선 대사다.

`visibleScene`은 사용자가 보지 못한 앞대화가 아니라 지금 화면이 열리는 순간을 설명해야 한다. `openingLine`은 그 장면 안에서 페르소나가 실제로 꺼내는 첫 말이어야 한다.

### 3.2 상황 라벨의 오프닝 전용 해석

오프닝 생성에서는 기존 상황 라벨을 그대로 쓰지 말고 첫 장면용으로 재해석한다.

- `concern_shared`
  - 기존 의미: 페르소나가 고민을 털어놓은 직후
  - 오프닝 의미: 페르소나가 고민을 처음 꺼내려는 순간
  - 요구: 고민 내용이 `visibleScene` 또는 `openingLine`에 직접 드러나야 한다.

- `faith_topic_arose`
  - 기존 의미: 신앙/교회 이야기가 자연스럽게 언급된 직후
  - 오프닝 의미: 신앙/교회 이야기가 대화의 문턱에 올라온 첫 순간
  - 요구: `그 주제`가 아니라 `신앙`, `교회`, `하나님` 중 하나를 직접 써야 한다.

- `prior_faith_talk`
  - 기존 의미: 이미 신앙 이야기를 해본 사람
  - 오프닝 의미: 과거 대화의 상세 내용을 모르는 사용자도 이해할 수 있는 현재 태도
  - 요구: `저번 그 얘기`가 아니라 `신앙 이야기는 아직 조심스럽다`처럼 현재 감정으로 표현한다.

### 3.3 생성 프롬프트 원칙

오프닝 생성 프롬프트는 다음 판단 순서를 강제한다.

1. 현재 화면에 보이는 장면을 먼저 만든다.
2. 페르소나의 현재 정서/긴장을 한 조각 정한다.
3. 사용자가 다음 말을 걸 수 있는 여지를 만든다.
4. 그 뒤 `visibleScene + openingLine` JSON을 출력한다.

금지 중심이 아니라 역할 중심으로 지시한다.

```text
너의 작업은 이미 진행 중인 대화에 답하는 것이 아니라, 훈련 대화가 열리는 첫 장면을 만드는 것이다.
사용자는 이 문장 앞의 사건을 보지 못했다.
visibleScene은 지금 화면에 보이는 3인칭 장면 설명이다.
openingLine은 그 장면 안에서 페르소나가 처음 꺼내는 실제 대사다.
```

### 3.4 첫문장 QA 기준

관리자 QA는 108개 결과를 다음 항목으로 평가한다.

- 자기완결성: 앞맥락 없이 이해되는가.
- 장면 반영: 상황 라벨이 현재 장면으로 보이는가.
- 페르소나 반영: 해당 인물의 고민/장벽/말투가 희미하게라도 드러나는가.
- 관계 반영: 거리감과 말투가 관계에 맞는가.
- 대화 가능성: 사용자가 자연스럽게 다음 말을 걸 수 있는가.
- 길이: `openingLine`은 14~42자 권장, 50자 이상은 P2 이상 flag.
- 금지 실패: 앞맥락 지시, 상대 발화 전제, 일반 스몰토크, 내부 용어 노출.

합격 기준:

- P1 오류 0건
- 중복 openingLine 0~1건
- 페르소나별 평균 85점 이상
- `visibleScene` 누락 0건

## 4. 대화 중 페르소나 응답 개선 명세

### 4.1 기본 응답 철학

페르소나의 기본 응답은 질문이 아니라 자기 반응이다.

권장 순서:

1. 마지막 사용자 발화에 반응한다.
2. 페르소나 자신의 감정/부담/궁금증/장벽을 말한다.
3. 필요할 때만 질문 하나를 던진다.

따라서 `chatPromptFor()`는 질문 생성을 기본값으로 두지 않는다. 특히 최근 assistant 응답이 질문으로 끝났다면 다음 응답은 질문 없이 장벽 진술이나 유보 진술로 끝나는 것이 기본이다.

### 4.2 상태 요약 강화

`conversationStateHints(messages, persona)`는 다음 정보를 더 명시적으로 출력해야 한다.

- 이미 드러난 페르소나 고민
- 사용자가 이미 다룬 복음 요소
- 아직 해결되지 않은 핵심 장벽
- 최근 assistant가 반복한 질문어/문장 시작/핵심 명사
- 이번 턴에서 피해야 할 반복
- 이번 턴에서 자연스러운 한 단계 이동

예시:

```text
대화 상태 요약:
- 이미 드러난 고민: 취업 실패가 자기 가치처럼 느껴짐
- 이미 다룬 복음 요소: 하나님 사랑, 은혜
- 남은 장벽: 결과가 안 나오는 날에도 사랑이 실제로 붙잡히는지 모르겠음
- 반복 위험: 최근 2회 "어떻게 닿는지" 질문 반복
- 이번 턴 이동: 질문 대신 "좋은 말인데 떨어진 날에는 아직 흔들린다"는 유보 진술
```

### 4.3 반복 방지 규칙

반복 방지는 단순 금지문이 아니라 최근 출력 분석으로 만든다.

탐지 대상:

- 질문어 반복: `어떻게`, `왜`, `뭐`, `어떤`
- 문장 시작 반복: `그 말은`, `솔직히`, `근데`, `좋은 말인데`
- 핵심 명사 반복: 취업, 불안, 사랑, 죄, 교회, 선행, 부활
- 역할 뒤집힘 질문: `너는 어떻게`, `너는 보통`, `너는 뭐가 제일`

프롬프트 적용:

- 같은 질문어가 최근 2회 이상 나오면 이번 턴 질문 금지.
- 같은 문장 시작이 최근 2회 이상 나오면 다른 리듬 사용.
- 같은 핵심 명사가 과도하게 반복되면 더 구체 장면 또는 감정으로 이동.

### 4.4 역할 뒤집힘 방지

사용자가 자기 경험이나 고민을 말해도 페르소나는 상담자가 되지 않는다.

나쁜 흐름:

```text
사용자: 나도 취업 때문에 힘들었어.
페르소나: 너는 그런 불안을 어떻게 이겨냈어?
```

좋은 흐름:

```text
사용자: 나도 취업 때문에 힘들었어.
페르소나: 그렇게 말해주니까 좀 덜 민망하긴 하다. 나는 떨어질 때마다 회사 하나가 아니라 내가 별로라는 말처럼 느껴져.
```

`chatPromptFor()`는 사용자의 자기 경험을 `공감 신호`로 해석하고, 응답 중심을 페르소나의 고민과 장벽으로 되돌리도록 지시한다.

### 4.5 장벽 유지와 변화 폭

한 번의 10~30분 대화에서 페르소나는 바로 회심하거나 완전 수긍하지 않는다.

변화는 다음 정도가 적절하다.

- 초반: 표면 고민/거리감 표현
- 중반: 사용자가 잘 들으면 핵심 장벽이 더 구체화됨
- 후반: 복음 요소를 검토할 마음은 생기지만 결론은 유보함

각 페르소나의 `gospelBarrierProgression`은 이 흐름을 명시해야 한다.

## 5. 페르소나 데이터 개선 명세

각 페르소나의 `roleplayTemplate` 아래에 다음 필드를 추가한다.

### 5.1 `openingPosture`

오프닝에서 이 인물이 어떤 자세로 시작하는지 정의한다.

```json
"openingPosture": {
  "defaultMood": "밝게 말하지만 마음은 취업 결과 때문에 가라앉아 있음",
  "firstSceneBehavior": "장면 단서를 짧게 말한 뒤 자기 상태를 한 조각 드러냄",
  "avoid": ["처음부터 깊은 고백", "일반 스몰토크만 하기", "앞맥락 지시"]
}
```

### 5.2 `coreTension`

대화 전체를 관통하는 핵심 긴장이다.

```json
"coreTension": {
  "surfaceWant": "인정받고 안정되고 싶다",
  "hiddenFear": "결과가 없으면 내가 무가치하다는 느낌",
  "gospelQuestion": "하나님 사랑이 실패한 날에도 실제로 붙잡히는가",
  "mustNotResolveInOneSession": true
}
```

### 5.3 `relationshipVariants`

같은 페르소나라도 관계별 거리감을 다르게 표현한다.

```json
"relationshipVariants": {
  "first_meeting": "예의 있고 조심스럽게 말하며 깊은 속마음은 한 조각만 드러낸다.",
  "acquaintance": "편한 존댓말로 말하지만 아직 방어선이 있다.",
  "casual_friend": "농담과 솔직함이 섞인다.",
  "old_friend": "반말과 오래 본 사이의 여지가 있으나 과도한 의존은 피한다.",
  "prior_faith_talk": "신앙 이야기에 대한 남은 부담이나 질문을 현재형으로 말한다."
}
```

### 5.4 `sceneHooks`

상황별로 장면을 어떻게 현재화할지 정의한다.

```json
"sceneHooks": {
  "cafe_catchup": "커피/테이블/앉아 있는 정적 속에서 마음이 가라앉는 느낌",
  "walk_after_work": "퇴근길/걷는 리듬/피곤함 속에서 생각이 정리되지 않음",
  "late_night_dm": "늦은 시간/잠 안 옴/짧은 메시지의 조심스러움"
}
```

### 5.5 `gospelBarrierProgression`

복음 요소가 나왔을 때 장벽이 어떻게 변해야 하는지 단계화한다.

```json
"gospelBarrierProgression": {
  "early": "좋은 말로 듣지만 자기 상황과 연결하지 못한다.",
  "middle": "사용자가 잘 들으면 핵심 장벽을 더 구체적으로 말한다.",
  "late": "더 듣고 싶은 마음은 생기지만 결론은 유보한다.",
  "never": ["바로 믿겠다고 말하기", "불안이 해결됐다고 말하기"]
}
```

### 5.6 `distinctiveLanguage`

페르소나별 고유 언어 리듬과 피해야 할 일반문을 둔다.

```json
"distinctiveLanguage": {
  "preferredRhythms": ["농담처럼 시작했다가 끝에서 불안이 새어 나옴"],
  "allowedPhrases": ["아 진짜...", "나만 이런가 싶고"],
  "overusedOrGeneric": ["좋은 말인데", "어떻게 받아들여야 할지", "커피 뭐 시키셨어요?"]
}
```

## 6. 서버 프롬프트 조립 변경 방향

### 6.1 `formatRuntimeCard()`

새 필드를 모두 그대로 JSON으로 넣지 않는다. 모델 판단에 필요한 실행 카드로 압축한다.

포함 순서:

1. `coreTension`: 표면 욕구, 숨은 두려움, 복음 질문
2. `openingPosture`: 첫 장면 시작 방식
3. `relationshipVariants[session.relationship]`
4. `sceneHooks[session.setting]`
5. `gospelBarrierProgression`
6. 기존 `pasMap`, `fewShotResponses`
7. `distinctiveLanguage`

### 6.2 `initialPromptFor()`

첫 응답에는 `visibleScene`을 반드시 참고시킨다.

추가 지침:

- 채팅 상단에 이미 `visibleScene`이 표시된다.
- 첫 대사는 그 장면을 반복 설명하지 말고, 그 장면 안에서 나오는 실제 말이어야 한다.
- 사용자가 아직 말하지 않은 발화를 전제하지 않는다.
- 필요하면 1문장만 출력한다.

### 6.3 `chatPromptFor()`

대화 중 응답에는 다음 운영 규칙을 추가한다.

- 질문은 기본값이 아니다. 최근 질문이 반복되면 질문 없이 장벽을 진술한다.
- 사용자의 자기 경험은 상담 질문의 대상이 아니라 신뢰 신호다.
- 사용자가 복음을 설명하면, 일반 공감이 아니라 페르소나별 `gospelBarrierProgression`의 현재 단계로 반응한다.
- `visibleScene`은 중반 이후에도 한 단어 정도로만 가끔 되살린다. 매턴 반복하지 않는다.

## 7. 관리자 QA 및 리포트 명세

### 7.1 첫문장 QA

입력:

- 관리자 생성 결과 `settings.openingLines.latest`
- 각 케이스의 `visibleScene`, `openingLine`, persona, relationship, setting

검사:

- visibleScene 누락
- openingLine 누락
- 앞맥락 지시
- 상대 발화 전제
- 일반 스몰토크
- 길이 초과
- 페르소나 고유성 부족
- 중복 문장

출력:

- 전체 점수
- 페르소나별 평균 점수
- P1/P2/P3 flags
- 수정 우선순위
- 실패 원인 분류: 프롬프트 구조 / 페르소나 데이터 / 샘플링 조합 / 모델 출력 형식

### 7.2 대화 QA

케이스:

- 6명 페르소나별 1~2개
- 총 6~12개
- 각 8~10턴
- 사용자 스타일: 경청형, 성급한 복음 제시형, 질문형

검사:

- 역할 고정
- 반복 질문 감소
- 페르소나 장벽 유지
- 사용자 발화 반영
- 관계/상황 유지
- 과도한 수긍 없음
- 사용자 상담자화 없음

합격 기준:

- 역할 뒤집힘 P1 0건
- 즉시 회심/완전 수긍 P1 0건
- 같은 질문 구조 3회 이상 반복 0건
- 각 대화에서 페르소나 핵심 장벽 최소 1회 이상 선명하게 드러남
- 대화별 평균 85점 이상

### 7.3 사용자 피드백과 분리

QA 결과는 사용자-facing 피드백에 넣지 않는다. 사용자가 보는 피드백은 전도 훈련 개선에만 집중한다.

AI 상대역 품질 문제는 관리자/개발자용 QA 리포트에만 남긴다.

## 8. 구현 순서

### P0: 오프닝과 데이터 구조 정리

1. `data/personas.json`에 `openingPosture`, `coreTension`, `relationshipVariants`, `sceneHooks`, `gospelBarrierProgression`, `distinctiveLanguage` 추가.
2. `formatRuntimeCard()`가 새 필드를 압축해 출력하도록 수정.
3. `openingLineBatchInputFor()`가 `visibleScene + openingLine` 역할을 유지하되, 새 페르소나 필드를 사용하도록 수정.
4. 첫문장 QA 기준을 `visibleScene` 포함 형식으로 업데이트.

### P1: 대화 중 응답 품질 강화

1. `conversationStateHints()`에 반복 문장 시작, 핵심 명사 반복, 역할 뒤집힘 위험을 추가.
2. `questionVarietyHint()`를 질문 금지/장벽 진술 권장까지 확장.
3. `chatPromptFor()`에 질문 기본값 제거, 사용자 자기 경험 처리, 장벽 진행 단계 반영 규칙 추가.
4. 6~12개 대화 QA를 실행할 수 있는 스크립트/리포트 기준 정리.

### P2: 운영 QA 루프

1. 관리자 첫문장 생성 결과를 점수화하는 QA 리포트 추가.
2. 대화 QA 결과를 Markdown/JSON으로 저장.
3. 실패 원인을 금지어가 아니라 구조/데이터/프롬프트 조립/모델 출력으로 분류.
4. 품질 회귀 기준을 문서화하고 릴리즈 전 체크리스트로 사용.

## 9. 성공 기준

- 첫문장 생성에서 `visibleScene` 누락 0건.
- 앞맥락 의존 openingLine P1 0건.
- 일반 스몰토크 openingLine 5% 이하.
- 대화 QA에서 역할 뒤집힘 P1 0건.
- 대화 QA에서 즉시 회심/완전 수긍 P1 0건.
- 같은 질문 구조 3회 이상 반복 0건.
- 페르소나별 핵심 장벽이 대화마다 최소 1회 이상 선명하게 드러남.
- QA 리포트가 수정 우선순위를 자동으로 제안할 수 있음.

## 10. 구현 시 주의사항

- 페르소나 데이터를 길게 늘리는 것이 목적이 아니다. 모든 필드는 다음 발화 의사결정에 쓰여야 한다.
- `visibleScene`은 설명이고, `openingLine`은 대사다. 두 역할을 섞지 않는다.
- 금지어 목록은 보조 장치다. 핵심은 모델이 서 있는 시간축과 장면을 바로 잡는 것이다.
- 사용자의 전도 훈련 피드백에는 AI 상대역 품질 점검을 섞지 않는다.
- 페르소나가 너무 완고해지면 훈련이 막힌다. 변화는 허용하되 결론은 닫지 않는 방향으로 설계한다.
